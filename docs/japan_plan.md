# 일본판 계획 — 받을 데이터·팩 분할·작업 순서·배포

- 작성 2026-10-21. 근거는 `docs/research/japan.md`(PLATEAU 건물 팩·일본 GSI DEM 조사, 같은 날)와 이 문서의 [로컬] 확인이다. 표기는 research와 같다: **[공식]**·**[로컬]**·**[추정]**·**확인 필요**.
- 상태: **J1(DB) 승인 대기.** 승인할 항목은 §6에 있다.

---

## 0. 결론

1. 일본판을 별도 플러그인으로 만들지 않는다. 지금 Global 모드가 일본 대상지에서 쓰는 데이터를 공공데이터로 바꾼다. 데이터 모드도 새로 만들지 않는다.
2. 새로 받는 데이터는 둘이다. 건물은 PLATEAU 팩이고, 지형은 일본 GSI(国土地理院 — 일본 국토교통성 소속 측량 기관, 한국 국토지리정보원과 다른 곳)의 DEM 타일을 실행 중에 받는다. 도로·수계·녹지·철도는 지금처럼 OSM을 쓴다.
3. PLATEAU 도시 데이터셋 하나를 팩 하나로 만든다(`jp<시구정촌코드>_context.db`, 경위도). 가장 큰 요코하마도 약 440 MB(xz 약 70 MB)로 추정한다. 한국 최대 팩(제주시 723 MB, xz 126 MB)보다 작으므로 더 나누지 않는다.
4. 일본 팩은 전부 지금 쓰는 Hugging Face 데이터셋과 매니페스트에 넣는다. 일본 데이터는 국외 반출 제한이 없어서 국내 서버가 필요 없다.
5. 순서는 J1 DB → J2 런타임 → J3 일본어 UI → J4 배포다. J1은 두 번 승인받는다. 먼저 파일럿 4개 도시를 만들고, 그 결과를 본 뒤 전국 빌드와 업로드를 한다.
6. 가장 큰 일은 데이터가 아니라 J3 일본어 UI다. 패널과 메시지가 전부 한국어로 박혀 있다.

## 1. 받을 데이터

| 요소 | 출처 | 받는 방식 | 1차 |
|---|---|---|---|
| 건물 외곽·높이·층수·용도 | PLATEAU `bldg` — LOD0 외곽 + LOD1 높이 | 팩(HF). 생성할 때 범위에 걸리는 도시만 | 넣음 (J1·J2) |
| 지형 | GSI DEM5A → 5B → 5C 타일, 셋 다 없으면 AWS | 실행 중(지금 AWS 타일 자리) | 넣음 (J2) |
| 도로·철도·수계·녹지·역·시설 | OSM Overpass | 실행 중 | 지금 그대로 |
| PLATEAU 밖 건물(시구정촌의 82 %) | OSM | 실행 중 | 지금 그대로. 높이는 대부분 기본값 |

받지 않는 것:
- **PLATEAU LOD2 지붕·텍스처**: 구니타치에서 LOD2는 0.7 %뿐이었다. 용량만 늘고, 컨텍스트에는 LOD1 압출이면 충분하다.
- **PLATEAU의 다른 지물(지형 `dem`·도로 `tran`·교량 등)**: 원본 1.46 TB의 대부분이 DEM이다. 지형은 GSI 타일로 대신한다.
- **2025 오사카 엑스포 회장(`27999`)**: 철거 중인 임시 행사장이다.
- **지적(일본 法務省 등기소 지도)**: 도시부 정비율이 낮다(DID 27 %). 그래서 일본에서는 `lots` 방식을 쓰지 않고 `area`·`point`만 쓴다.
- **노후도**: 구니타치의 PLATEAU 건축 연도 채움률이 0 %였다.

나중 후보(2D 단계에서 따로 승인): 용도지역(PLATEAU `urf` 또는 国土数値情報 A29), 일본 주소 검색(GSI 주소 검색 API — 지금은 Nominatim).

## 2. 팩 분할·형식 (DB 계약)

- **단위**: PLATEAU 데이터셋 하나가 팩 하나다. 시구정촌 코드는 5자리이고, 정령시는 시 전체 코드 하나다(예: 요코하마 `14100`). 도시마다 최신 연도판 하나만 쓴다. 모두 306개다.
- **이름**: `jp<코드>_context.db`(+`.xz`)이고, HF 경로는 `jp/jp<코드>_context.db.xz`다. `jp`를 붙이는 이유는 둘이다.
  - 일본 코드가 한국 시군구 코드와 겹친다(예: `11110`).
  - 배포된 플러그인(0.2.2 이하)은 이름이 숫자 5자리로 시작하는 팩만 고른다. 그래서 일본 항목을 같은 매니페스트에 넣어도 구버전은 무시한다 [로컬: `cmd_site.get_area_packs`·`_download_for_generate`, `context_builder.get_pending_packs`, 패널은 `download_data`에 항상 `names`를 보낸다].
- **좌표**: 경위도 EPSG:4326, 소수 7자리(약 1 cm)다. JGD2011과 WGS84는 수 cm 차이라 같은 것으로 본다. 매니페스트 `bounds`도 경위도 `[서, 남, 동, 북]`이다.
- **표**: 한국 컨텍스트 팩의 `buildings` 칸 이름·순서를 그대로 쓴다. 일본 팩끼리는 `data_pack.open_union`(UNION ALL)으로 묶이므로 모든 일본 팩의 칸이 같아야 한다. 여기에 `data_sources` 한 줄(도시·연도·출처 문구·라이선스)을 더하고, `PRAGMA user_version = 1`로 둔다.

| 칸 | 값 |
|---|---|
| `building_id` | 시구정촌 코드 × 10⁷ + 순번. 팩끼리 겹치지 않는다 |
| `src_key` | `plateau:<gml:id>`. 도시 경계 중복을 이것으로 걸러 낸다 |
| `geometry_json` | `lod0RoofEdge`를 쓰고, 없으면 `lod0FootPrint`, 그것도 없으면 `lod1Solid` 바닥면을 쓴다. 바깥 링만, `[경도, 위도]` |
| `height_m`·`height_src`·`height_grade` | `measuredHeight`가 2~500 m면 B `plateau_height`다. 없으면 층수 × 층고로 C `plateau_levels`, 그것도 없으면 기본값 D다. `osm_context.get_building_height`와 같은 등급이다 |
| `grnd_flr`·`ugrnd_flr` | `storeysAboveGround`·`storeysBelowGround` |
| `ngii_kind` | 원천 용도 코드 그대로(예: `411`). OSM 갈래가 `building` 태그를 여기에 두는 것과 같다 |
| `usability` | 비워 둔다. 한국 용도 대분류로 바꾸는 표는 런타임 상수다(J2). 표를 고쳐도 팩을 다시 배포하지 않는다 |
| `footprint_area_sqm` | 외곽 면적 ㎡. 빌드 때 국소 투영으로 잰다 |
| `source_id`·`reference_date` | `plateau`·데이터셋 연도 |
| 나머지(`pnu`·`ngii_*`·대장 칸) | NULL |

- **결측값** [로컬, 구니타치 45,215동]: 층수 `9999`(13.6 %)와 높이 `-9999`는 '모름'이라는 뜻이다. 값으로 쓰면 9,999층 건물이 생기므로 0으로 바꾼다. 층수가 `9999`인 6,155동은 모두 용도도 `461`(불명)이었다.
- **크기** [추정]: 도시별 건물 GML 크기(research §5 실측)를 구니타치 1동당 13.1 KB로 나누고, 한국 팩 1동당 0.6 KB를 곱했다. 중앙값은 약 29 MB, 상위 10 %는 125 MB 이상, 최대는 요코하마 약 440 MB다. 한국 컨텍스트 팩의 xz 압축비(실측 약 6배)를 쓰면 전체 압축본은 약 2~3 GB다. LOD2가 많은 도시는 실제보다 크게 잡힌다.

## 3. 빌드 — `scripts/dev_plateau.py` 한 파일 (표준 라이브러리만)

1. **`catalog`**: G空間情報センター CKAN `package_search`로 도시별 최신 CityGML zip의 URL·연도·이름을 모아 `data/raw/plateau/catalog.json`에 둔다. 카탈로그 API 리다이렉트는 404를 내므로 쓰지 않는다(research §3).
2. **`build [코드…]`**: zip을 HTTP Range로 열어 `udx/bldg/*_op.gml`만 흘려 읽는다(`iterparse`). 원본 zip은 통째로 받지 않고 남기지도 않는다. 도시별로 병렬 처리한다.
3. **쓰기**: `build/packs/jp<코드>_context.db`를 만들고 xz로 압축한 뒤 매니페스트 항목을 넣는다(`bounds` 경위도, `year`, `label` "東京都 国立市 建物" 꼴). 한국 항목은 건드리지 않는다.
4. **올리기**: `dev_deploy.py upload`가 `jp/` 팩도 올리도록 고친다. 지금은 숫자로 시작하지 않는 팩을 공개 매니페스트에서 뺀다(`# 옛 시도 팩`). 데이터셋 카드에는 PLATEAU 출처·가공 사실·CC BY 4.0 절을 더한다.

- **어디서**: 이 Mac에서 돌린다(여유 공간 271 GB). 받는 양은 18.1 GB다. 풀면 344 GB인 XML은 디스크에 쓰지 않고 흘려 읽는다. 시간은 받기 몇 시간에 파싱 1~3시간으로 추정한다.
- **갱신**: PLATEAU 새 연도판이 나오면(연 1회 안팎) `catalog` 차이로 바뀐 도시만 다시 빌드해 올린다.

## 4. Hugging Face 전략 평가 — 타당하다, 단 저장소·CDN으로만 쓴다

**타당한 이유**
- 일본 데이터는 국외 반출 제한이 없고 CC BY 4.0과 호환된다. 공개 데이터셋에 그대로 올릴 수 있다.
- 무료이고 CDN·Range를 지원한다. 익명 받기 한도는 IP당 5분에 3,000회다 [로컬: 응답 헤더 `ratelimit-policy: q=3000;w=300`]. 사용자 한 명이 한 번에 받는 팩은 몇 개뿐이다.
- 필지 팩과 매니페스트가 이미 HF에 있다. 새 계정·서버·비용이 없다.
- 매니페스트가 팩마다 주소를 따로 적는다. HF에 문제가 생기면 주소만 바꿔 옮기고, 플러그인은 고치지 않는다.
- CORS를 허용한다 [로컬]. 웹판(Pyodide)도 바로 받을 수 있다. 국내 서버 팩은 지금 이것이 막혀 있다.

**주의할 점**
- 무료 공개 저장 공간은 'best-effort'다. HF 문서는 처음 몇 GB를 넘으면 다른 사용자에게 실제로 가치 있는 것만 올려 달라고 한다. 지금 약 8 GB이고 일본이 약 2~3 GB 늘어난다[추정]. 그래서 LOD2·텍스처·원본·중간 산출물·Parquet 사본처럼 용량만 늘리는 것은 올리지 않고, 데이터셋 카드를 충실히 쓴다.
- 그래도 막히면 PRO(월 $9, 공개 저장 10 TB)로 올리거나 다른 정적 호스팅으로 주소만 바꾼다.

**HF로 하지 않을 것**

| 하지 않을 것 | 이유 |
|---|---|
| 빌드 연산(HF Jobs·Spaces) | Jobs는 유료이고, Spaces는 배치 작업용이 아니다. 연 1회 안팎 도는 빌드는 이 Mac이면 된다 |
| GSI DEM 타일 미러 | 신청 없이 쓸 수 있는 것은 실시간 읽기뿐이다. 저장·재배포는 일본 測量法 승인 대상일 수 있다 |
| 일본 OSM을 미리 팩으로 굽기 | ODbL 재배포 의무와 갱신 부담이 생긴다. 사용 통계에서 Overpass 실패(`osm_failed`)가 많아지면 다시 검토한다 |
| 한국 수치지형도 팩 옮기기 | 한국 공간정보관리법 제16조. 지금처럼 국내 서버에 둔다 |

## 5. 단계와 승인 지점

| 단계 | 내용 | 완료 기준(눈으로 보는 것) | 승인 | 일수[추정] |
|---|---|---|---|---|
| **J1a 파일럿** | `dev_plateau.py`로 4개 도시: 국립시(작음·실측 있음), 신주쿠구(고층·밀집), 도요나카시(2020년도 옛 사양), 요코하마시(가장 큼) | 팩 4개, 도시별 동 수·높이 등급 비율·팩 크기 표, 높이 색 미리보기 SVG, 테스트 1개(작은 GML 조각 → 행) | §6 승인 뒤 바로 시작 | 1 |
| **J1b 전국** | 306개 빌드 → HF 업로드 + 매니페스트 | HF `jp/`에 팩 306개, 구버전 플러그인 동작은 그대로 | 파일럿 보고 뒤(업로드는 공개 행위) | 1~2 |
| J2 런타임 | 아래 목록 | 신주쿠·국립 3dm에서 PLATEAU 높이 건물이 GSI 지형 위에 선다 | J1b 뒤 | 2~3 |
| J3 일본어 UI | 패널·메시지 문자열 분리 + 일본어. 영어도 같은 틀이라 같이 하기를 권한다 | 일본어 브라우저에서 패널이 일본어로 뜬다 | 별도 | 4~6 |
| J4 배포 | 0.3.0(Yak·Blender·SketchUp), 웹사이트·스토어 설명 일본어, 출처 고지 | 공개 | 별도 | 1 |

J2에서 고칠 것:
- `data_pack`: 일본 팩은 경위도 `bounds`로 겹침을 판정한다. 한국 조회의 `get_local_paths`는 `jp` 파일을 뺀다.
- 생성 직전 받기: `get_query_bounds`가 Global이면 None을 돌려준다. 일본이면 경위도 범위를 돌려주게 해서 걸리는 일본 팩을 받는다. 지도 칩은 필요 없다(일본에는 필지 고르기가 없다).
- `osm_context.load`: 범위에 일본 팩이 있으면 PLATEAU 건물을 쓰고, PLATEAU와 겹치지 않는 OSM 건물만 보탠다. 도시 경계 밖과 PLATEAU 이후 신축이 여기에 해당한다.
- 지형: research §9.4대로 GSI DEM으로 바꾼다.
- 출처 줄: PLATEAU(도시·연도)·GSI(国土地理院)·OSM을 적는다.
- 용도 매핑 상수(`PLATEAU_USAGE`)를 둔다.
- `X-UDT-Client` 헤더: 지금은 필지 팩이 아니면 보낸다. 국내 서버 주소일 때만 보내게 바꾼다. 그대로 두면 설치 ID가 HF로 간다.

- 데이터를 플러그인보다 먼저 올려도 된다. 구버전은 일본 항목을 무시하고, 새 플러그인(J2)은 올라가 있는 팩을 바로 쓴다.
- GSI DEM 교체는 J1과 독립이고 반나절 일이다. 원하면 J1보다 먼저 할 수 있다.
- J3 규모: 한국어가 든 줄이 패널 456줄, `cmd_site.py` 180줄, `context_builder.py` 305줄이다(주석 포함, 2D 도면 문구는 별도).

## 6. 승인 요청 — J1 착수 전

1. **범위**: PLATEAU 건물만 받는다(LOD0 외곽 + LOD1 높이·층수·용도). 306개 도시 최신판이고, 엑스포 회장·LOD2·텍스처·다른 지물은 뺀다.
2. **분할**: 도시 데이터셋 하나가 팩 하나다. 이름은 `jp<코드>_context.db`, 좌표는 경위도, 칸은 한국 `buildings`와 같다.
3. **호스팅**: 지금 HF 데이터셋의 `jp/` 폴더와 같은 `manifest.json`에 넣는다. 별도 저장소는 만들지 않는다.
4. **용도 코드**: 원천 코드를 그대로 저장한다. 한국 용도 대분류 매핑은 런타임 상수로 둔다.
5. **진행**: 파일럿 4개 도시를 만들어 결과를 보고한다. 전국 빌드와 업로드는 그 뒤에 다시 승인받는다.

## 7. 확인 필요

- **용도 코드표**: `Building_usage.xml` 원문을 J2 매핑 전에 확인한다.
- **일본 測量法**: PLATEAU 공공측량 성과 제약과, GSI 타일을 3dm 메시로 남기는 것이 승인 대상인지 J4 공개 전에 확인한다.
- **`measuredHeight` 기준**: 지반 최저점부터 최고점까지인지 표준제품사양서에서 확인한다.
- **`reference_date`**: 연도판 연도로 둘지, 실제 조사 시점(도시계획기초조사)으로 둘지 정한다. 기준일 경고 임계(`SOURCE_AGE_THRESHOLDS`)와도 맞춰야 한다.
