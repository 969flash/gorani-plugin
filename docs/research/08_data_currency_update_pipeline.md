## 0. 요약 — 결론과 추천

1. **새 판 감지는 "페이지 목록의 기준일"로 한다.** 브이월드 국가중점데이터 상세 페이지는 파일마다 `구분(전체데이터/변동데이터)·기준일·갱신일`을 표시하고, 쿼리 `fileGbnCd=AL&sidoCd=11`을 붙이면 **서울 전체본의 약 1년치 등재 이력**이 그대로 보인다(§1.1). 서울 단위 월간 전체본은 GIS건물통합정보 129 MB(기준일 2026-02 판부터 매월 9일, 2025-11~2026-01 판은 4일), 연속지적도 93~105 MB(매월 8일, 같은 변경 이력), 토지이용계획 속성 CSV 96~150 MB(매월 9일경, 08-26판만 96 MB — §1.3 이상치)+공간 SHP 분기, 토지이동이력 33 MB(매월 말일; 단 2025-12~2026-06 7개 판이 2026-07-24 일괄 게시), 토지특성은 반기(기준 2026-05-20, 갱신 2026-07-10). 게시는 기준일보다 0일~2개월(토지이동이력은 최대 ~7개월) 늦다. 별도의 "등재 이력 페이지"는 없다 [공식].
2. **변동분('일간'이라 표기되지만 실측은 영업일 기준·결측일 있음, §1.2)은 구조가 확인됐지만 쓰지 않는다.** 컬럼 정의서 '테이블정의서(변동)' 시트에서 `CH_D010`(GIS건물)·`CH_D002`(연속지적)·`CH_D157`(토지이동이력)·용도지역지구 변동 SHP는 전체본 컬럼 + `변동순번` + `입력구분`(1자, 샘플 `U`·`I`) 구조다. **삭제(철거) 레코드가 `입력구분=D`로 오는지는 정의서 코드표에 없어 실제 변동 파일로 확인 필요**. 토지특성·토지이용계획은 변동 시트 자체가 없다(전체본 교체만). 1인 개발에서는 **월간 전체본 교체**가 변동분 병합보다 단순하고 오류가 적다 → 일간 변동분은 채택하지 않는다(§1.2, §4).
3. **철거 반영 = 월간 전체본 diff(기본) + 건축HUB 대용량(월간) 폐쇄말소대장·철거멸실관리대장 벌크(서울 전역 `buildings.status`) + 대상지 단위 건축HUB API(보강).** 건축물대장 API(15134735)에는 철거 오퍼레이션이 없고, **건축인허가정보 API(15136267)의 `getApDemolExtngMgmRgstInfo`(철거멸실관리대장: `demolExtngGbCd`·`demolStrtDay`·`demolEndDay`·`demolExtngDay`)** 와 **폐쇄말소대장정보 API(15137093)의 `getSrTitleInfo`(`shterGbCd`·`shterDay` 폐쇄말소일)** 가 철거·멸실을 준다. 세 API 모두 `startDate/endDate(YYYYMMDD)` 파라미터와 `crtnDay`(생성일자) 필드를 갖는다 [공식]. 서울시 전용 철거·멸실 공개 데이터셋은 공공데이터포털 검색에서 없었다(서울시 건축인허가 기본개요·층별개요 CSV 2025-08-14판만 있고, 그마저 포털 메타가 '수시(1회성 데이터)'라 지속 갱신 원천이 아니다). 건축HUB 대용량 목록 1페이지에 '폐쇄말소대장 표제부 (2026년 08월), 데이터제공년월 2026-09'가 있어 서울 전역 철거·말소를 월 1회 벌크로 받을 수 있다(§2.1·§2.3 E)(§2).
4. **토지이동(분할·합병·지목변경)은 토지이동이력정보(dsId=13)로 잡는다.** 토지특성정보에는 이동사유·종전지번 필드가 없다(A0~A26 전부 확인). 토지이동이력정보는 CSV(`AL_D157`/변동 `CH_D157`), 전체-월간·변동-'일간'(실측 결측일 있음), `토지이동사유코드`(20·21 분할, 30·31 합병, 40 지목변경, 43 지번변경, 44 면적정정, 45 경계정정 …)·`토지이동일자`·`토지이동말소일자`·`폐쇄순번`을 가진다. GIS건물통합정보 SHP에는 `A2 고유번호(PNU)`가 이미 있으므로 건물 `pnu`는 **공간조인이 아니라 원천 PNU를 우선** 쓰고, 공간조인은 PNU 결측·토지이동 발생 필지에만 재계산한다(§3).
5. **DB는 현행 `source_id + reference_date` 유지 + `source_files` 1표만 추가.** 스냅샷 테이블·SCD2(`valid_from/valid_to`)는 하지 않는다. 전체본 교체는 트랜잭션 안에서 `DELETE … WHERE source_id=? ; INSERT …`, 교체 전 DB 파일 1장 복사가 스냅샷이다. 적재 스크립트는 **원천 파일 sha256·페이지 기준일**을 `source_files`에 기록하고 해시가 같으면 적재를 건너뛴다(§4).
6. **산출물 표기 문자열(제안)**: `자료기준 — 필지: 국토교통부 토지특성정보 2026-05-13 · 건물: 국토교통부 GIS건물통합정보 2026-09-09 · 도시계획: 서울특별시 UPIS 2026-09 · 지형: 국토지리정보원 수치지형도 1:5,000 Ver2.0(도엽 37705072 외 3, 제작/수정연도 확인 필요) · 좌표계 EPSG:5186 · 생성 2026-10-07`. 근거: 지도도식규칙 제8조(외도곽에 편집연도·수정연도·인쇄연도), 수치지도 작성 작업규칙 제11조·국토지리정보원 고시 제7조(메타데이터에 이력·범위), 도시·군관리계획수립지침 1-5-1-1(기준년도=기초조사 착수 시점)·[별첨1] 6.(도면 종류·규격), 도시·군기본계획수립지침 3-3-1(4)(**자료출처 명시, 최신자료 사용**), 지구단위계획수립지침 2-5·[별첨1] 3-1(3)·4-1(2) [공식]. 서울시 도시계획 도면의 '기준일' 표기 관행은 원문을 열지 못해 **확인 필요**(§5).
7. **경고 임계값(원천 기준일 경과 개월)**: 월간 원천(GIS건물·연속지적·토지이동·UPIS·토지이용계획 속성)은 **3개월 경과 AND §4.3 새 판 감지 '새 판 있음'** 두 조건이 모두 참일 때만 노란 경고(브이월드 게시가 기준일보다 46~53일, 토지이동이력은 최대 ~7개월 늦은 실측이 있어 '2개월' 고정 임계값은 새 판이 나오기 전에 상시 발동한다), 토지이용계획 공간 5개월(같은 조건), 토지특성 8개월(반기), 수치지형도 1:5,000 18개월(국토지리정보원 "1년 주기" 갱신 + 배포 지연), 1:1,000 84개월(평균 5~7년 수시), API 캐시(LT_C_BLDGINFO·건축HUB) 1개월(§5.3).
8. **갱신 체크리스트**: 월 1회 ≈ 30~40분(GIS건물 서울 129 MB 수동 1건 + UPIS 자동 + 토지이용계획 CSV 150 MB 수동 1건), 반기 1회 ≈ 1~2시간(토지특성 25개 구 SHP 수동 + 필지 DB 재빌드), 연 1회 ≈ 반나절(수치지형도 139도엽 중 변경 도엽 재수령). 대상지 생성 시 API 호출은 자동(§6).

### 4.2 최소 변경 — `source_files` 표 추가 (DDL)

```sql

CREATE TABLE IF NOT EXISTS source_files (
    source_id   TEXT NOT NULL,            -- data_sources.source_id
    file_name   TEXT NOT NULL,            -- 예 AL_D010_11_20260909.zip / 37705072.zip / UQ111_…_202609.zip
    sha256      TEXT NOT NULL,
    size_bytes  INTEGER,
    listed_date TEXT,                     -- 페이지 목록의 기준일(또는 파일명 날짜, 수치지형도는 제작년도)

);
```

### 4.3 적재 스크립트 규칙 (해시·기준일로 재적재 판정)

```python
# dev_context_builder.py 공통부 (ponytail: 파일 단위 전체 교체, 변동분 병합 없음)
import hashlib, sqlite3, datetime, pathlib

def sha256(p: pathlib.Path) -> str:
    h = hashlib.sha256()
    with p.open("rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)
    return h.hexdigest()

def norm_date(s: str) -> str:
    """'2024/01/18' · '2024-01-18' · '20240118' → '2024-01-18' (정의서 샘플에 세 형식이 섞여 있음, 아래 참고)"""
    s = s.strip().replace("/", "-").replace(".", "-")
    return f"{s[:4]}-{s[4:6]}-{s[6:8]}" if len(s) == 8 else s

def needs_load(con: sqlite3.Connection, source_id: str, p: pathlib.Path) -> bool:
    row = con.execute("SELECT sha256 FROM source_files WHERE source_id=? AND file_name=?",
                      (source_id, p.name)).fetchone()
    return row is None or row[0] != sha256(p)

def replace_source(con, source_id, p, listed_date, load_rows):
    """전체본 교체: 한 트랜잭션. 실패하면 이전 판이 그대로 남는다."""
    with con:  # BEGIN … COMMIT/ROLLBACK
        con.execute("DELETE FROM buildings WHERE source_id=?", (source_id,))
        load_rows(con)                     # INSERT … (source_id, reference_date=norm_date(레코드 A22))
        con.execute("""INSERT OR REPLACE INTO source_files VALUES (?,?,?,?,?,?)""",
                    (source_id, p.name, sha256(p), p.stat().st_size, listed_date,
                     datetime.datetime.now().astimezone().isoformat(timespec="seconds")))
```
- 적재 전 한 줄 스냅샷: `cp data/seoul_context.db data/backup/seoul_context_$(date +%Y%m%d).db` (교체 실패·비교용). 3판 넘으면 오래된 것 삭제.
- `listed_date` 입력원: 브이월드는 목록 기준일(파일명 날짜와 같음), 열린데이터광장은 등록일, 수치지형도는 `sheets.csv`의 제작년도, API 캐시는 호출일.
- 새 판 자동 감지(선택, 10줄): 월 1회 `GET dtmk_ntads_s002.do?svcCde=NA&dsId=18&fileGbnCd=AL&sidoCd=11` 을 받아 첫 행 기준일이 `source_files.listed_date`보다 크면 콘솔에 "새 판 2026-10-09 있음 — 받아서 data/raw/vworld_GIS건물통합정보/ 에 두세요" 출력(다운로드는 로그인 필요라 사람이). 기준일 규칙이 바뀌어도(4일→8~9일, §1.2) 대소 비교라 영향 없다. 이 결과('새 판 있음/없음')는 §5.3 경고의 두 번째 조건으로도 쓴다 — 새 판이 없으면 기준일이 3개월 지나도 원천 측 지연으로 보고 경고를 억제한다. dsId=13·14·23도 같은 URL 패턴(`dsId`만 교체)으로 함께 점검.
- `reference_date` 형식 정규화: 컬럼 정의서 샘플은 `AL_D010 A22 데이터기준일자 '2024/01/18'`(슬래시), `A28 데이터생성변경일자 '2011-01-13'`(하이픈), `AL_D002 A6 '2024-01-18'`로 섞여 있다(테이블정의서(전체) 788·794·852행). 위 `norm_date()`로 `YYYY-MM-DD` 10자로 맞추고, 길이가 10이 아닌 값이 나오면 적재를 중단한다(검증 1줄).
- `dev_database_builder.py`(보유)는 `reference_date`를 상수(`"2026-02"`)로 박고 해시를 쓰지 않는다(37행 주석 "새 공개본 검증 후 seq/reference_date/file_name을 함께 갱신") → 같은 `source_files` 규칙으로 맞추면 두 DB의 표기가 일관된다.
